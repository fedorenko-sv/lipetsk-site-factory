## Решение и команда

Один проект, общее ядро Booking/Lead, контент и темы через конфигурацию. Текущий результат — рабочее синтетическое демо Auto и минимальный Beauty на том же ядре. Calculator — следующий этап после обратной связи; B2B RFQ — под заказ. Публичный запуск клиента требует его согласованных входных данных.

Канал получения заявок выбирается отдельно для каждого заказчика: Telegram, почта или существующая CRM через подходящий адаптер. Настройка серверная; интерфейс и API заявки одинаковы. В первый релиз конкретного клиента подключается один согласованный канал, остальные добавляются по спросу.

| Роль | Ответственность |
| --- | --- |
| Архитектор, этот чат | Контракты, решения по архитектуре, интеграция, Git, финальная проверка и решение о готовности |
| Antigravity, выбранная пользователем 3.8 Next | Весь интерфейсный блок и его unit/browser-тесты |
| Hermes | Весь серверный блок и его unit/PostgreSQL/HTTP-тесты |

## Начало работы

Node.js 22 LTS, npm; версии зависимостей закреплены в package-lock.json. Не перегенерировать проект через create-next-app поверх этого репозитория.

```powershell
npm ci
npm run verify:architecture
npm run dev
```

Начальная страница сообщает, что демо готовится. Форма и маршрут /api/leads появятся в ветках разработчиков; текущая сборка не является рабочим приёмом заявок.

Проверка архитектурного старта проверяет документы, схемы/примеры, lint, типы и сборку. Это не проверка будущей бизнес-логики.

## Передача двум разработчикам

Передать каждому свой запрос из [START_FULL_BLOCKS.md](agents/START_FULL_BLOCKS.md). Antigravity продолжает codex/frontend-pr3, Hermes — codex/backend-pr3. У каждого отдельная папка. Существующие F1 и B1-fix сохраняются; актуальный main включается обычным merge, без reset/rebase/force push.

GitHub-задачи: [интерфейс](https://github.com/fedorenko-sv/lipetsk-site-factory/issues/1), [сервер](https://github.com/fedorenko-sv/lipetsk-site-factory/issues/2). Выполнять актуальные большие ТЗ полностью. Каждый сдаёт один итоговый Draft PR с SHA, результатами проверок и таблицей покрытия ID сценариев; промежуточное одобрение микрошагов не требуется.

Исторические маленькие задания и ранние ревью остаются в Git как контекст. Их замечания включены в полный пакет; отдельно сдавать их снова не нужно. Проверки возможностей моделей в текущую работу не входят.

Разработчики могут начинать параллельно после архитектурного базиса: у интерфейса есть примеры HTTP-ответов, у сервера — схема запроса. Тестовый транспорт интерфейса разрешён только в тестах; публичное демо не имитирует отправку.

После двух итоговых PR архитектор объединяет ветки в отдельном checkout и запускает npm run verify:release с настоящей тестовой БД, затем проверяет мобильный путь вручную. Только после этого принимается решение о слиянии в main и demo-ready.

## Ограничения выпуска
