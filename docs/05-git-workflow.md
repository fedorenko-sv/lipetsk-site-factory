# Работа через Git

## Постоянные правила

main — интегрированное состояние, за него отвечает архитектор. Два разработчика коммитят в своих ветках; их код попадает в main после проверки. Если используется один GitHub-аккаунт, имена Git-веток обозначают роли, а не разные права доступа.

| Роль | Ветка | Отдельный checkout |
| --- | --- | --- |
| Архитектор | main, при необходимости codex/integration-pr3 | Исходный репозиторий |
| Разработчик 1 | codex/frontend-pr3 | frontend |
| Разработчик 2 | codex/backend-pr3 | backend |

## Старт в разных компьютерах/чатах

```powershell
git clone https://github.com/fedorenko-sv/lipetsk-site-factory.git
cd lipetsk-site-factory
git switch --track origin/codex/frontend-pr3
npm ci
```

Разработчик 2 использует codex/backend-pr3. Если ветка уже существует локально, достаточно git switch с её именем.

На одном компьютере архитектор создаёт worktree вне основного репозитория, в work/ папки задачи. Это два checkout одного Git-репозитория, не две независимые кодовые базы. Нельзя открывать одну и ту же папку для одновременного редактирования разными агентами.

## Каждая итерация

1. Прочитать AGENTS.md и своё ТЗ, проверить git status и ветку.
2. Обновить сведения: git fetch origin.
3. Если ветка только собственная, включить актуальный main командой git merge origin/main. Это сохраняет историю без force push. Rebase допускается только до публикации собственных коммитов.
4. Сделать ограниченный законченный шаг, проверить поведение, коммит.
5. git push -u origin с именем своей ветки.
6. Открыть Draft PR в main: проблема, итоговое поведение, проверки, скриншоты/ограничения. Прикреплять синтетические данные.

Названия коммитов: feat(ui): ..., feat(leads): ..., fix(...): ..., docs(...): ... . Авторство Git остаётся реальным настроенным пользователем; не подменять identity ради роли агента.

## Общие файлы

contracts/**, src/shared/api.generated.ts, package.json/package-lock.json, tsconfig, CI, env-шаблон и настройки deployment меняет архитектор. Разработчик отправляет текст запроса: причина, предлагаемая зависимость/поле, пример запроса и влияние на другую ветку. Архитектор проверяет, коммитит в main и сообщает SHA; оба включают этот коммит.

Ни один разработчик не переписывает API под свой текущий UI. Изменение 1.0.0 должно иметь совместимый переход или одновременное обновление обоих исполнителей.

## Порядок интеграции

Небольшие PR допустимы по этапам. Финальная интеграция: backend → frontend → общий прогон → исправления своих областей. Тесты интерфейса с подменённым HTTP не заменяют общий прогон с БД.

Автор PR обновляет свою ветку при конфликте в своей области. Архитектор разрешает конфликт общих контрактов/настроек. Не снимать чужие проверки и не удалять тест ради зелёного статуса.

## Контроль на GitHub

Желаемая настройка main: только PR, зелёный quality, разрешённые обсуждения, запрет force push/удаления. Возможность применить настройки проверяется на тарифе репозитория.

Если все агенты используют fedorenko-sv, GitHub не превращает их в независимых ревьюеров. Не включать обязательное независимое approval, которое нельзя получить в этой модели. Приёмка архитектора фиксируется отчётом с SHA и merge только после него. CODEOWNERS — подсказка маршрутизации, не доказательство независимого ревью.

Если защита private main недоступна по тарифу, регламент остаётся обязательным организационно; не утверждать, что GitHub технически запретил прямой push. Фактический ответ о настройке записать в отчёт старта.

## Сдача ветки

- Ссылка на PR или имя ветки и SHA.
- Кратко: что теперь делает пользователь/сервер.
- Команды и результаты проверок; реальные ограничения отдельно.
- Для UI: актуальные скрины 360/390/430 и desktop.
- Для backend: миграции, конкурентные запросы, получение/повтор уведомления на синтетике.
- Нет секретов, баз, персональных данных и необъяснённых изменений чужих файлов.
