# Раздельный запуск шести демо — приёмка 18.11.2026

Пакет поверх a8e854e; worktree portfolio, ветка codex/six-prototypes, PR #5. Подготовлен следующий пункт передачи: выбранный сайт запускается собственным процессом и тестовым хранилищем из одного production build.

## Результат

| Возможность | Реализация |
| --- | --- |
| Выбор одного демо | DEMO_SITE_KEY на runtime; CLI preview:demo. |
| Собственный вход | / -> /demo/<key>, 307 внутри origin, query сохранён. |
| Собственные разделы | Каталог, карточки, информация, форма и privacy сохраняют прежние URL. |
| Закрытые чужие страницы | 404/noindex, включая RSC/prefetch, encoded-имена и похожие префиксы. |
| API scope | Точное соответствие выбранному профилю; Auto включает свой OBLIK. |
| Ошибочная конфигурация | Неизвестный профиль: страницы 503/no-store/noindex; неправильный scope: API 503 DEMO_NOT_READY. |
| Данные | Отдельные origin/БД/секреты/recording-назначения на каждый preview-процесс. |
| Исходная фабрика | Пустой профиль, прежний порт 3035, все 69 маршрутов и старая команда. |
| Завершение | Останавливается только свой child; state содержит публичную метаинформацию. |

Новых зависимостей и новых HTTP-полей нет. Цены, Booking A, Calculator B, идемпотентность, квитанции и worker остаются общими. Static/dynamic разделение маршрутов сохранено. API исключены из matcher Proxy; собственные обработчики продолжают проверять Origin, тело, схему, scope и секрет internal route.

Это подготовка публичных демонстрационных сайтов с отдельными БД; система авторизованных арендаторов/кабинетов сюда не добавляется. Общие публичные ассеты и код входят в одну сборку.

## Красные и зелёные проверки

На исходной версии два теста показывали проблему: выбранный Beauty принимал широкий API allowlist; неизвестное имя профиля игнорировалось. DP01/DP02: 2 failed, 1 passed в начальном запуске. Отдельный Next-процесс с DEMO_SITE_KEY=beauty отдавал фабрику 200 вместо собственного перенаправления 307.

После реализации DP01–DP08 и DO01–DO05 проходят. Первая проверка нового redirect выявила ошибочное предположение harness об абсолютном Location; стандартный относительный адрес теперь разрешается относительно своего origin.

В общей приёмке намеренно задан родительский DEMO_SITE_KEY=beauty. Это выявило BI14: вложенный тестовый сервер наследовал режим оператора и получал правильный защитный 503. Исправлена среда самого тестового runner и его дочерних серверов на явный factory. Серверный guard сохранён. После исправления 53/53 integration и 13/13 system прошли в том же родительском окружении.

## Проверка шести настоящих профилей

test:demo-profiles использует один build. Для каждого профиля создаёт уникальную test-БД, запускает Next на временном loopback-порту и проверяет:

1. Собственный вход, каталог, форму, privacy; один H1 и noindex.
2. Чужие страницы, RSC/prefetch, encoded-адреса и похожие префиксы; shared fonts доступны.
3. Валидную чужую заявку и чужой Origin: 404/403; в БД 0 leads, 0 outbox, 0 rate-limit rows.
4. Настоящий browser -> API -> PostgreSQL: leadId UI совпадает с сохранённой заявкой.
5. Повтор ключа: HTTP 200 и одна запись.
6. Настоящий outbox/recording: sent, один receipt и собственный destination.
7. Публичный state без DSN/HMAC/token; завершение child и освобождение порта.
8. Очистку только новых БД, принадлежность которым подтверждена уникальным run ID.

Дополнительно два настоящих misconfigured Next-процесса проверяют typo и неверный scope. Они используют недоступный dummy storage: ожидается DEMO_NOT_READY до обращения к нему.

Набор выполнен без mocks и skip. Browser для сквозной проверки отдельных процессов — Chromium; презентационная регрессия коллекции проходит Chromium/WebKit. Реальный iPhone не объявляется проверенным.

## Найденная в CI регрессия медиаплеера

На первом коммите пакета 3a5c9c8 [Quality](https://github.com/fedorenko-sv/lipetsk-site-factory/actions/runs/44300356944) и [backend](https://github.com/fedorenko-sv/lipetsk-site-factory/actions/runs/44300356938) прошли. Серверный CI подтвердил 70 unit, 53 integration, 13 system и все шесть отдельных профилей с двумя ошибочными конфигурациями. Во [frontend](https://github.com/fedorenko-sv/lipetsk-site-factory/actions/runs/44300356920) прошёл 151 browser-тест; DT11 WebKit не увидел кнопку ручного запуска после внедрённого отказа play() за штатные пять секунд.

Проверены screenshot, error-context и trace этого запуска. Отказ вызова play() уже зафиксирован тестовым счётчиком, однако MP4 продолжает загружаться, а кнопка появляется позже. У видео обнаружены два независимых пути запуска: HTML autoplay и управление play() из эффекта видимости. Прежняя подмена play() не контролировала нативный путь целиком. Эти наблюдения не доказывают конкретную причину задержки декодера.

В PhotoFilm оставлен один управляемый путь автоматического воспроизведения: видимость, настройки экономии/движения, пауза и отказ проверяются одним эффектом; при отказе видео сразу ставится на паузу. Muted, loop и playsInline сохранены. DT11 дополнен проверками paused и отсутствия событий playing до разрешённого запуска, затем проверяет настоящий запуск с выбранного кадра. Таймаут реакции интерфейса не увеличен, retries и skip не добавлены.

Отдельное поведение autoplay и вызова play() описано в первичных источниках: [WebKit: video policies](https://webkit.org/blog/6784/new-video-policies-for-ios/) и [HTML: media elements](https://html.spec.whatwg.org/multipage/media.html#attr-media-autoplay). Решение о правке основано на коде и trace проекта; финальная приёмка — реальные Chromium/WebKit.

После правки локально повторно пройдены lint/typecheck и 20/20 проверок медиаплеера: DT01/DT02/DT07/DT09/DT11, по два запуска в Chromium и WebKit. Fail, flaky, skip — 0; [команда и исходная статистика](isolated-demo-profiles/media-followup.json). Полный CI запускается на следующем коммите с этой правкой.

## Что остаётся открытым в общем плане

- Долговременная удалённая БД и публичные HTTPS-адреса: нужны выбранные окружение/домен и поручение на публикацию.
- Клиентский запуск: материалы, тарифы, политики и способ получения заявок конкретного заказчика.
- Настоящий канал администратора: выбранный адаптер и отдельная проверка доставки.
- Core C/RFQ, второй предметный расчёт, ночная бронь и ёмкость групп: отдельный подтверждённый сценарий.

Локальный compose использует tmpfs; он не объявляется долговременным хранилищем. Реальная публикация, сообщения, оплата и live-сбор данных не выполнялись.
