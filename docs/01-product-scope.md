# Продукт и границы

## Цель

Получить проверяемый мобильный путь «вижу цену → выбираю услугу и удобное время → оставляю заявку» для первого разговора с авто-бизнесом. Бизнес-результат измеряется ответами, созвонами и внедрениями; техническая команда не обещает количество продаж.

PR-3 и PR-4 — названия продуктовых выпусков из исходных документов, не номера GitHub pull request.

## P0: PR-3 Авто, ориентир 10.11.2026

1. Шаг 1: нейтральный демо-бренд, оффер, 3–5 услуг и цены, контакт/адрес только при наличии подтверждения; CTA виден с мобильного первого экрана.
2. Шаг 2: услуга, относящиеся к ней параметры, предпочтительная дата/время; ресурс скрыт для Auto. Текст: «Выберите удобное время — мастер подтвердит». Предпочтение не проверяет свободную ёмкость.
3. Шаг 3: сводка, телефон, необязательное имя, отдельное неотмеченное согласие и ссылка на политику, отправка, результат или повтор без потери данных.
4. Сервер: нормализация, проверка конфигурации, антиспам, устойчивость к повторам, транзакционное сохранение и отложенное уведомление.
5. Мобильные размеры 360/390/430 и desktop 1280+, доступность клавиатурой, корректные ошибки и контраст.
6. Свидетельства: по одному мобильному скрину каждого шага, короткое прохождение и отчёт о заявке end-to-end после подключения инфраструктуры.
7. Два typed/schema-checked конфига Auto/Beauty для проверки границ переиспользования. Полноценный Beauty-дизайн не является P0.

Результат после отправки — состояние шага 3, а не четвёртый обязательный экран.

## P1 после приёмки PR-3

- PR-4 Beauty: журнальная тема, услуги и мастера, то же ядро и API; ориентир 11–20 ноября.
- Полу-персонализация через конфиг за 30–60 минут как цель для готового контента, без обещания сроков всем клиентам.
- Фактическая воронка: page_view, price_view, booking_start, service_selected, time_preference_selected, lead_submit_success/error, click_call/messenger. В P0 фиксируем типы/места вызова, внешний сбор выключен до решения владельца. Без телефона, имени и произвольных строк.
- Calculator: сначала окна → предварительная цена с допущениями → заявка на замер. Повторно использовать обработку лида, не UI Booking целиком. Расширить контракт отдельно до начала реализации.
- Только после одного сквозного кейса — мебель и клининг как конфигурации калькулятора.

## P2 по подтверждённому спросу

Реальное расписание и атомарная бронь, напоминания клиенту, оплата/сертификаты, групповые занятия, размещение с ночами/сезонностью, медицинская оболочка, каталог/RFQ и интеграции 1С. Глэмпинг — ориентир февраль–март 2027, если спрос подтвердится.

## Что не включаем

CRM, кабинеты клиентов, онлайн-оплату, SMS, отправку сообщения клиенту по одному номеру в Telegram, 30 независимых демо, массовую персонализацию 68 лидов и рассылки.

## Режимы

- **demo:** заметный баннер, синтетические данные, noindex. До реализации серверного demo-адаптера отправка недоступна; после — только фиксированный тестовый номер и тестовое хранилище. Нельзя показывать «успех» без сохранения.
- **live:** только утверждённый оператор/политика, реальные контакты/прайс, долговременная БД и проверенный канал администратора. Изолированные окружение и БД для клиента.

Публичное demo с отключённым приёмом и рабочий live-релиз — разные результаты; отчёты должны указывать режим.
