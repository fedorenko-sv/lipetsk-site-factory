# Финальная приёмка архитектором

Проверяется код на конкретном commit и конкретное окружение. Отчёт: дата, SHA, режим demo/live, выполненные команды, результаты, ссылки на свидетельства и ограничения. Отчёты разработчиков — вход для проверки, не её замена.

## Уровни проверки

1. Статика: схемы и примеры согласованы; typecheck/lint/build; поиск секретов без печати значений.
2. Unit: нормализация, текущие конфиги, дата/время, правила повтора и состояния UI.
3. Integration: реальный PostgreSQL, транзакции, конкурентные запросы, ограничения, outbox/lease/rate limit.
4. Browser: Playwright Chromium и WebKit, мобильные viewport, HTTP errors/timeout, сохранение формы.
5. Общий путь: браузер → реальный route → тестовая БД → worker → согласованный endpoint канала. На финальном рабочем стенде повторить с реальной настройкой уведомлений.

Подмена транспорта допустима для UI-тестов, но не в общем сценарии. WebKit на компьютере не равен проверке на реальном iPhone; если телефон не проверен, это прямо указать.

## Сценарий ручной проверки

- Открыть /demo/auto в нужном режиме; подтвердить маркировку данных и текста времени.
- Пройти три шага, вернуться назад, поменять услугу, ещё раз сверить цену.
- Ошибиться в телефоне и согласии, исправить и отправить.
- Сопоставить leadId интерфейса с БД/outbox и уведомлением администратора.
- Воспроизвести сетевую ошибку, двойное нажатие и успешный повтор.
- Переключить конфиг на Beauty, не трогая ядро, повторить основной путь.
- Проверить политику, актуальность контактов/изображений, CTA и noindex.

## Критерий решения

**release-ready** требует всех применимых P0 и утверждённых live-входов. **demo-ready** допускает отсутствие реального канала/оператора только при выключенном сборе реальных данных и явной маркировке. Любой ложный успех, потеря лидов, утечка данных или обещание подтверждённой брони — changes-required.

До фактического запуска продукта здесь нет утверждения «все Q пройдены». В отчёте архитектурного старта проверяется только основа репозитория.
