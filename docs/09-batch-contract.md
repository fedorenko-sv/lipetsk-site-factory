# PR3-BATCH-2 — общий контракт двух больших блоков

Версия задания: 05.11.2026. Это актуальное соглашение для всего PR-3. Предыдущие задания B1/F1 и промежуточные замечания включены в большие блоки; отдельной сдачи по ним больше нет.

Исполнители: Hermes — сервер; Antigravity с выбранной пользователем 3.8 Next — интерфейс. Каждый самостоятельно заканчивает весь свой блок. Архитектор принимает итоговые ветки и проводит один общий финальный контроль.

## Источники и приоритет

1. Текущее поручение владельца и AGENTS.md.
2. contracts/openapi.json и contracts/site-config.schema.json — синтаксис публичных данных.

4. agents/PR3_BACKEND_HERMES.md или agents/PR3_FRONTEND_ANTIGRAVITY.md — полная работа соответствующего исполнителя.
5. Старые дорожные карты и маленькие задания — исторический контекст; их указания «сдать один шаг и остановиться» к этому пакету не применяются.

Общие TypeScript-типы уже закреплены в src/shared/contracts.ts. Это явные типы по JSON-схемам, не автоматически сгенерированный файл. Runtime-валидация на сервере выполняется по JSON-схемам. Не создавать независимые копии LeadCreateRequest, LeadReceipt или SiteConfig.

## Ожидаемый результат

Полноценный демонстрационный Core A: Auto и минимальный Beauty → три шага → одна долговременно сохранённая заявка → outbox → проверяемое локальное получение через recording-адаптер.

Клиентский реальный канал не выбран. В этом пакете обязательны NotificationPort, реестр, версионированные назначения и recording-адаптер. Telegram, email и CRM подключаются под заказчика следующим изменением. Ни один канал не назначается общим по умолчанию. Recording не выдавать за получение заявки настоящим администратором.

Публичный live-сбор остаётся закрытым до появления утверждённых данных оператора, политики и реального канала. Реальные сообщения, платная инфраструктура, публикация и рекламные обращения этим пакетом не разрешены.

## Запрос

~~~json
{
  "siteKey": "auto",
  "configVersion": "demo-2026-11-04",
  "kind": "booking",
  "serviceId": "tire-change",
  "serviceOptions": { "wheel-size": "R16" },
  "preferred": {
    "date": "2026-11-06",
    "time": "10:30",
    "timezone": "Europe/Moscow"
  },
  "customer": { "phone": "+70000000000" },
  "consent": { "accepted": true, "version": "demo-2026-11-04" },
  "antiBot": { "website": "" }
}
~~~

Дата примера — пример wire-формата. Unit-тесты используют фиксированные часы, HTTP/browser-тесты выбирают актуальную будущую рабочую дату. Не привязывать успешный тест навсегда к 6 ноября.

Обязательные заголовки: Content-Type application/json и Idempotency-Key UUID. Origin соответствует серверному allowlist. Допускается Content-Type с charset=utf-8. Все ответы API: Cache-Control no-store.

Клиент не передаёт цену, статус, consentAt, createdAt, канал, destinationKey, chat_id, webhook URL, роль или настройки оператора. Неизвестные поля отклоняются.

## Ответ и ошибки

Успех 201; идентичный успешный повтор 200:

~~~json
{
  "leadId": "00000000-0000-4000-8000-000000000001",
  "status": "received",
  "replayed": false,
  "message": "Заявка получена. Администратор подтвердит удобное время."
}
~~~

Для повтора replayed=true, leadId прежний. Успех означает COMMIT lead + outbox. Он не подтверждает слот, отправку уведомления или срок звонка.

~~~json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Проверьте поля формы.",
    "requestId": "00000000-0000-4000-8000-000000000002",
    "fieldErrors": { "customer.phone": "Укажите корректный телефон." }
  }
}
~~~

| HTTP | code |
| --- | --- |
| 400 | INVALID_JSON, IDEMPOTENCY_REQUIRED — ключ отсутствует либо не UUID |
| 403 | ORIGIN_NOT_ALLOWED |
| 404 | SITE_NOT_FOUND |
| 409 | IDEMPOTENCY_CONFLICT, CONFIG_CHANGED, CONSENT_CHANGED |
| 413 | PAYLOAD_TOO_LARGE |
| 415 | UNSUPPORTED_MEDIA_TYPE |
| 422 | VALIDATION_FAILED, REQUEST_REJECTED для заполненного honeypot |
| 429 | RATE_LIMITED; Retry-After — целое число секунд |
| 500 | INTERNAL_ERROR без внутренних деталей |
| 503 | STORAGE_UNAVAILABLE, DEMO_NOT_READY, LIVE_NOT_READY |

Общие пути fieldErrors: serviceId, resourceId, serviceOptions.{optionId}, preferred, preferred.date, preferred.time, customer.phone, customer.name, consent.accepted, consent.version. Ошибки схемы сопоставлять с этими путями, а не отдавать пользователю сырые ошибки Ajv.

## Единые правила

- Телефон: существующая normalizePhone из backend-ветки, формы +7/8, ASCII-цифры, только U+0020/U+00A0 как пробелы. Unicode-разделители и управляющие символы отклоняются. Demo принимает только +70000000000, live этот номер отклоняет.
- Имя необязательно. Интерфейс обрезает пробелы и не отправляет пустое имя. Сервер отклоняет переданную пустую/состоящую из пробелов строку, длина после trim не более 80.
- Выбор услуги/опций/ресурса — только из конфигурации. Неизвестные и несовместимые значения отклоняются. Пустой resourceId не отправляется.
- День недели: ISO 1=понедельник ... 7=воскресенье. Дата имеет смысл в Europe/Moscow независимо от часового пояса браузера/сервера.
- Предпочтение строго в будущем, дата не позже московского today + horizonDays включительно. Время начала: opens включительно, closes исключительно, кратность timeStepMinutes относительно opens.
- Для P0 валидируется время начала. Длительность услуги информационная; ёмкость, пересечения и реальная бронь отсутствуют.
- Изменение цены не моделируется через wheel-size. Показывать исходную цену/«от» и пояснение; сервер сохраняет её снапшот.
- Consent accepted строго true. Версия совпадает с конфигом; время согласия задаёт сервер.
- Attribution выключена по умолчанию. При выключенном сборе сервер её отбрасывает; при включённом допускает только три ключа из схемы до 80 символов.
- Телефон/имя не хранятся в URL, localStorage/sessionStorage, аналитике, логах или session replay. Контакт в UI живёт в памяти страницы.
- Сохранённый идентичный повтор проверяется до актуальных бизнес-проверок даты/версии и до расходования лимита. Базовые защиты HTTP, схема и honeypot выполняются всегда.
- Ограничение частоты относится к новым валидным заявкам: 5/10 минут на site+IP и 100/час на site. Сохранённые повторы, включая конкурентные, не увеличивают счётчик. Для этого допустима транзакционная сериализация по siteKey+Idempotency-Key; UNIQUE остаётся обязательным.
- Смена destinationKey влияет только на новые заявки. Уже сохранённая очередь использует прежнюю неизменяемую версию назначения.

## Проверки и команды

Общий инструментарий: Node 22, npm, встроенный node:test, Ajv, pg, Playwright Chromium/WebKit. Зависимости закреплены в package-lock.json. TypeScript-модули для Node-тестов импортируются относительными путями с .ts; это разрешено tsconfig.

| Команда | Ответственный |
| --- | --- |
| npm run verify:architecture | Общая статическая проверка и production build |
| npm run test:backend | Hermes: unit-тесты tests/backend/*.test.mjs |
| npm run test:integration | Hermes: безопасный harness реального PostgreSQL + HTTP |
| npm run verify:backend | Полная сдача сервера |
| npm run test:ui | Antigravity: чистая логика UI |
| npm run test:e2e | Antigravity: браузерные тесты с HTTP-подменами только в тестах |
| npm run verify:frontend | Полная сдача интерфейса |
| npm run test:system | Общий финальный браузер → API → PostgreSQL → recording |
| npm run verify:release | Финальный контроль архитектора после интеграции |

Команды предметных тестов обязаны падать при отсутствии тестов/нужной инфраструктуры, а не сообщать пустой зелёный результат. Стартовая база проверяется verify:architecture; наличие команд не означает, что функции уже реализованы.

Playwright-конфиги уже закреплены: frontend 127.0.0.1:3021, HTTP integration 3022, system 3023. Не использовать чужой уже работающий сервер и не завершать чужие процессы.

## Независимая работа и сдача

В своих ветках включить актуальный origin/main обычным merge. На чистой ветке без собственных коммитов fast-forward допустим. Исходные ветки содержат F1 (8d1542a) и B1-fix (bf5823e); их сохранять и развивать.

Каждый имеет одну рабочую папку. Общие файлы и контракт заморожены. Дополнительные изменения .env.example и server workflow разрешены Hermes; frontend workflow — Antigravity. Остальные области перечислены в своих ТЗ.

Разработчики выполняют все внутренние шаги самостоятельно, коммитят логические части и сдают один итоговый PR каждый. Не присылать промежуточные микроэтапы на одобрение. Обычные решения принимать самостоятельно в рамках контракта. При реальном внешнем блокере закончить независимые части и одним отчётом указать невыполненные проверки.

Архитектор соединяет backend → frontend, запускает verify:release и ручной просмотр. Только после этого — merge в main и решение demo-ready/release-ready/changes-required. Зелёный build не заменяет предметные тесты.
