# От механики заявки к полноценному демо-сайту: четыре итерации

Дата: 06.11.2026. Владелец плана: архитектор. Исполнители: два существующих разработчика, Hermes и Antigravity. Новых агентов не запускать.

Это план следующего продуктового этапа, подготовленный по запросу владельца о полноценном лендинге и остальных страницах. Он не запускает новую кодовую задачу поверх незавершённых текущих поручений. Текущие FR/BR7 заканчиваются своими сдачами; дальнейшие права на новые пути закрепляются перед стартом соответствующего блока.

**Цель:** получить два законченных демонстрационных сайта — Auto и Beauty — с выразительным первым экраном, содержательными страницами, общей рабочей заявкой и устойчивой ссылкой для показа.

У проекта два публичных уровня: презентационная главная фабрики / и главные клиентских примеров /demo/auto, /demo/beauty. Дизайн требуется обоим уровням. Уже в первой итерации появятся полноценный Auto hero и собранный первый экран самой витрины; третья итерация завершит витрину двумя готовыми примерами.

**Архитектура:** сохранить существующее ядро Booking/API/PostgreSQL/outbox. Достроить отдельный слой презентационного контента, общие шаблоны информационных страниц и две визуальные подачи. Первый экран заявки становится полноценным лендингом; дополнительных обязательных шагов перед отправкой не появляется.

**Стек:** существующие Next.js App Router, TypeScript, CSS/Tailwind, node:test и Playwright. Смена стека, новый CMS и новые библиотеки ради лендинга не требуются.

## 1. Что существует сейчас

По исходникам опубликованной реализации доступны пять пользовательских адресов:

| Путь | Содержание |
| --- | --- |

## 2. Почему возникло расхождение с ожиданием

Исходный PR-3 был описан как три мобильных экрана для первого разговора с бизнесом. Это ограничивало первоначальный выпуск механикой оффера и заявки.

В плане архитектора критерии надёжности и API были зафиксированы подробнее визуального и содержательного результата. Готовность механики недостаточно явно отделили от готовности полноценного сайта для показа. Это недостаток планирования и продуктовой приёмки.

Достройка ниже сохраняет уже сделанное ядро и добавляет недостающий внешний продукт. Рост числа информационных страниц не увеличивает число обязательных шагов заявки.

## 3. Какой результат считаем готовым демо

1. Главная Auto выглядит как законченный сайт автосервиса: сильный hero, услуги/цены, объяснение процесса, ответы на вопросы, контактный блок и рабочие CTA.
2. Есть законченные страницы каталога, отдельных услуг, о компании, контактов и политики.
3. Beauty использует то же ядро и шаблоны, но имеет самостоятельную композицию, изображения, типографику и контент.
4. Главная фабрики объясняет механику и показывает оба примера с реальными скриншотами.
5. Заявка действительно сохраняется; успех не подменяется анимацией; ошибки и повтор работают.
6. Демо явно обозначено, реальные данные не собираются. Отзывы, стаж, награды, мастера и фотографии реального заказчика не выдумываются.
7. Ссылка для показа доступна из согласованного окружения, а не зависит от незапущенного локального Docker.
8. Есть итоговый SHA, проверка страниц/формы, свежие кадры desktop/mobile и короткое прохождение.

До настоящего клиентского запуска отдельно нужны реальные материалы, канал, утверждённые данные оператора, окружение и правила хранения. Отсутствие этих live-входов не блокирует красивое синтетическое демо.

## 4. Карта страниц

Целевой набор формируется общими маршрутами:

| Страница | Маршрут | Задача |
| --- | --- | --- |
| Главная клиента | /demo/{siteKey} | Оффер, визуальная подача, цены, путь к заявке |
| Услуги | /demo/{siteKey}/services | Полный понятный прайс и переход к конкретной услуге |
| Одна услуга | /demo/{siteKey}/services/{serviceId} | Что входит, цена/«от», параметры, длительность, вопросы, CTA |
| О компании/подходе | /demo/{siteKey}/about | Подход к работе и процесс; только достоверные либо явно демо-материалы |
| Контакты | /demo/{siteKey}/contacts | Контакты/часы/как обратиться по имеющимся данным |
| Политика | /demo/{siteKey}/privacy | Правильный режим и условия тестовой формы |

Для Auto с текущими тремя услугами получится восемь адресов: главная, каталог, три услуги, о компании, контакты, политика. Для Beauty с двумя услугами — семь. Вместе с витриной фабрики — шестнадцать адресов, собранных из шести общих типов клиентских страниц.

Не создавать отдельную обязательную страницу записи, повторно заставляющую проходить оффер. На главной лендинг является шагом 1; CTA ведёт к шагу 2, затем к шагу 3. Информационные страницы дают прямой вход в тот же сценарий с выбранной услугой.

Общий навигационный контракт для входа с услуги: /demo/{siteKey}?service={serviceId}#request. В URL только публичный ID услуги; телефон/имя не передаются. Неизвестный ID не вызывает ошибку приложения и не подменяет сайт. На главной открывается та же форма с выбранной услугой; её бизнес-правила остаются общими.

Архитектор закрепляет общие типы, новые тестовые команды и владение путями одним базовым коммитом перед началом. Исполнители не ждут отдельного согласования каждого компонента.

Презентационные данные не меняют цену на сервере и не расширяют LeadCreateRequest. Один serviceId связывает лендинг, подробную страницу и существующий Booking.

Используется demo recording и синтетика. Подключение настоящего канала заказчика и live-сбора — отдельный разрешённый запуск, а не скрытое расширение этой итерации.

Приёмка:
- [ ] Публичный HTTPS URL подтверждён реальным открытием после разрешённой публикации.
- [ ] Все страницы и три основных сквозных сценария работают на опубликованном SHA.
- [ ] Нет обязательных skip, фиктивных assert или ложного успеха.
- [ ] Мобильный просмотр сравним по качеству с desktop, все CTA доступны.
- [ ] Локальная и опубликованная версии соответствуют одному зафиксированному снимку.

Если окружение ещё не предоставлено, статус — готово локальное демо / готово к публикации, а не опубликовано.

## 10. Ритм работы и экономия лимитов

Четыре итерации — четыре крупных проверяемых выпуска, а не четыре сообщения модели. Приёмочные дефекты устраняются внутри своей итерации; новые идеи попадают в следующий backlog, не создают бесконечные скрытые этапы.

- Каждый разработчик получает один цельный пакет с путями, входами, скринами результата и условиями сдачи.
- На Antigravity приходится работа, где важны композиция и визуальное решение.
- Hermes выполняет типовые страницы, конфиги, контентные проверки и системные сценарии после закрепления дизайн-компонентов. Его работа больше не ограничивается backend, которому не нужно постоянное переписывание ради лендинга.
- Перед перераспределением путей обновить AGENTS.md. Один файл не редактируют два агента одновременно.
- Новые ветки для презентационного слоя: codex/site-visual для Antigravity, codex/site-pages для Hermes, от принятой общей базы. Два отдельных worktree сохраняются.
- Архитектор готовит общий контракт/настройки и принимает итог блока, без промежуточной проверки каждой функции.
- В отчёте: SHA/PR, видимые изменения, команды/CI, кадры desktop/mobile, ограничения. Большие логи и весь чат повторно не пересылаются.
- Общий регрессионный запуск выполняется на интеграции; отдельный агент не повторяет чужой набор без изменения соответствующей части.
- Запрещены формальные тесты констант вместо поведения и бесконечные проверки возможностей модели.

Сначала завершить текущие технические исправления и зафиксировать общую исходную версию. Дизайн-бриф/контент можно готовить параллельно; новую вёрстку не накладывать на активные FR-правки в тех же файлах.
