- Не делегировать дальше без явного указания владельца. Эти ТЗ рассчитаны ровно на двух разработчиков и одного архитектора.

## Продуктовые инварианты

- Три шага: оффер/прайс → услуга/пожелание по времени → контакт/согласие/результат.
- Время — пожелание. Не писать «свободный слот», «бронь подтверждена», «осталось два места» без реальной системы расписания.
- Успех API — только после сохранения. Ошибка отправки уведомления не удаляет лид.
- Демо-данные явно помечать. Не придумывать отзывы, лицензии, сертификаты или реальные контакты.
- Любой публичный демо-стенд принимает только синтетические данные, если нет утверждённого live-режима.
- Цена берётся из серверной конфигурации, не доверять присланной цене.
- Собственная CRM, оплаты, 1С, реальные слоты и SMS не входят в P0. Доставка в существующую CRM возможна отдельным адаптером по требованиям заказчика.

## Данные и безопасность

- Секреты только в env. Не печатать DATABASE_URL, токены, телефон или тело заявки в логи и артефакты.
- Никаких NEXT_PUBLIC_* для секретов или серверных назначений уведомлений.
- Не коммитить базы лидов и копии исходных Google Docs.
- Не отправлять реальные сообщения, не публиковать публичный стенд и не создавать платные сервисы в ходе реализации без отдельного явного поручения.
- Канал уведомлений выбирается для каждого заказчика в серверной конфигурации; общего обязательного Telegram-канала нет. Права обработки данных определяются до live-запуска.
- Не собирать медицинские сведения через общую форму.

## Проверка и сдача

- Каждый разработчик самостоятельно выполняет весь большой блок и его тесты, затем сдаёт один итоговый PR. Промежуточной приёмки функций/экранов и проверок возможностей моделей нет. Архитектор выполняет только финальную интеграцию и контроль.
- Обычные решения внутри своей области принимать самостоятельно и фиксировать в отчёте. Реальный внешний блокер сообщать одним итоговым отчётом после завершения независимых частей; не выдавать непройденные проверки за успех.
- Проверять существенное поведение тестами: повтор запроса, потеря сети, отказ БД/уведомления, валидация и изоляция siteKey.
- Не добавлять тесты, которые лишь повторяют JSX или константы без проверки поведения.
- Перед сдачей: актуальный main, чистый diff, команды проверок и их фактический результат, ограничения.
- Скриншоты и видео — без персональных данных. Временные материалы хранить вне репозитория или в игнорируемом work/; финальные свидетельства — docs/reports/.
- Статус «готово» допустим только с проверяемыми результатами. Релизное решение принимает архитектор.
