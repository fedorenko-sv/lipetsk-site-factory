# PR-3 — полный интерфейсный блок для Antigravity

> Исполнитель: Antigravity с доступной пользователю 3.8 Next, разработчик 1. Режим: самостоятельная реализация всего документа, без субагентов и промежуточной сдачи микрозадач. Архитектор выполняет финальный контроль.

**Цель:** закончить мобильный путь Core A из трёх шагов, Auto и минимальную Beauty-оболочку на одном ядре, HTTP-клиент, ошибки/повторы, доступность и исполняемые тесты.

**Архитектура:** общий BookingFlow + чистое состояние + конфиги + CSS-токены. Transport работает по замороженному Lead API; сервер и база принадлежат Hermes. Подмена API допускается только в tests/e2e.

**Стек:** Next.js App Router, TypeScript, Tailwind, node:test для чистой логики, Playwright Chromium/WebKit для поведения браузера.

**Пакет:** PR3-BATCH-2, 05.11.2026. Ветка codex/frontend-pr3. Исходный F1 — commit 8d1542aae6185fcce4b45d75bc6bc4459abcf496; развивать его, не начинать проект заново.

## 1. Итог блока

- Auto: предложение/прайс → услуга, параметры, предпочтительное время → контакт, согласие, отправка и результат.
- Beauty: те же состояние, отправка, валидация и шаги; другая тема/услуги/мастера.
- Корректные happy/error/timeout/retry paths, без потери ввода на обычной ошибке.
- Смена UI-конфига не копирует ядро и не меняет HTTP-контракт.
- Клавиатурная доступность, 360/390/430 и 1280 px, Chromium/WebKit.
- Unit и браузерные тесты, актуальные скриншоты, короткое видео и итоговый PR.

Не входят: backend/API/БД, реальные свободные слоты, оплата, CRM, клиентские напоминания, новые отраслевые оболочки, генерация изображений и публикация.

## 7. Состояние ядра

Рекомендуемое размещение: src/features/booking/client/state.ts. Чистый reducer/функции переходов отдельно от JSX.

Минимальная модель:
- step: offer | preference | contact.
- serviceId, serviceOptions, resourceId?.
- preferred date/time/timezone.
- customer phone/name, consentAccepted.
- submit: idle | submitting | error | received.
- receipt/error, idempotencyKey и snapshot отправляемого payload в памяти.

Инварианты:
1. Назад/вперёд сохраняют совместимые поля.
2. Смена услуги удаляет неизвестные опции и несовместимого мастера; не оставляет старую сводку.
3. Изменение даты удаляет время, если оно стало недопустимым.
4. Переход вперёд требует только полей соответствующего шага.
5. Отправка невозможна при submitting, неверных полях/согласии.
6. Полученный результат относится только к текущей попытке; поздний ответ старого запроса не перезаписывает новый.
7. Успех возможен только после проверенного receipt HTTP 200/201.
8. Контакт не сохраняется вне памяти страницы. Полная ручная перезагрузка может его очистить; обычная API-ошибка — нет.
9. Для другой конфигурации состояние стартует заново, без переноса телефона/услуги между клиентами.

## 11. HTTP-клиент

Файл src/features/booking/client/lead-client.ts. Типы из src/shared/contracts.ts.

Согласованная сигнатура:
~~~ts
export interface SubmitOptions {
  idempotencyKey: string;
  signal?: AbortSignal;
  timeoutMs?: number;
}
export interface SubmitResult {
  httpStatus: 200 | 201;
  receipt: LeadReceipt;
}
export async function submitLead(
  body: LeadCreateRequest,
  options: SubmitOptions
): Promise<SubmitResult>;
~~~

timeoutMs по умолчанию 15000, используется AbortController; опция нужна для unit-теста, не для публичного env/API. Ошибка — typed object/class с httpStatus?, code?, requestId?, fieldErrors?, retryAfterSeconds? и kind network|timeout|http|invalid-response. UI не разбирает текст error.message для ветвления.

Поведение:
1. POST /api/leads, JSON, Idempotency-Key. Канал/адрес/цена в body отсутствуют.
2. UUID создаётся перед первой отправкой. Неизменённый повтор после неизвестного исхода сохраняет key/body.
3. Изменение отправляемых данных или исправление 422 создаёт новый key. Вернувшийся ответ прошлой попытки не меняет новую.
4. Никаких автоматических бесконечных POST/retry в useEffect.
5. HTTP 200/201 — успех только при корректном receipt: leadId, received, replayed, message. HTML/битый JSON/неверная форма даже с 200 — ошибка.
6. 422: fieldErrors у полей и доступная общая сводка.
7. 409 CONFIG_CHANGED/CONSENT_CHANGED: сохранить форму, показать, что сведения надо обновить; не повторять автоматически со старой версией/согласием.
8. Для P0 разрешена кнопка ручного обновления страницы с честным пояснением, что контакт понадобится ввести повторно. Самостоятельно не перезагружать страницу и не хранить телефон ради восстановления.
9. 429: Retry-After в секундах, отсчёт/доступный статус, сохранённый ввод, повтор после срока.
10. 400/403/404/413/415/500/503: безопасная ошибка, поля сохранены, без fake-success и stack.
11. При timeout/network key сохраняется; пользователь явно нажимает «Повторить».
12. Внешняя аналитика выключена. Допустим no-op adapter с фиксированными именами событий без PII и произвольных строк.

## 15. Исполняемый образец browser-теста

Файл tests/e2e/retry.spec.ts может использовать этот сценарий. Он не подменяет обработчики интерфейса, только HTTP.

~~~ts
import { test, expect } from "@playwright/test";

test("повтор после потери сети сохраняет данные и ключ", async ({ page }) => {
  const attempts: Array<{ key: string | undefined; body: unknown }> = [];
  await page.route("**/api/leads", async route => {
    const req = route.request();
    attempts.push({ key: req.headers()["idempotency-key"], body: req.postDataJSON() });
    if (attempts.length === 1) {
      await route.abort("failed");
      return;
    }
    await route.fulfill({
      status: 201,
      contentType: "application/json",
      body: JSON.stringify({
        leadId: "00000000-0000-4000-8000-000000000001",
        status: "received", replayed: false,
        message: "Заявка получена. Администратор подтвердит время."
      })
    });
~~~

## 16. Проверки, CI и артефакты

~~~sh
npm ci --prefer-offline --no-audit --no-fund
npx --no-install playwright install chromium webkit
npm run verify:frontend
~~~

Перед browser-тестами build уже выполнен verify-командой. Конфиг поднимает собственный production сервер на 3021. Не переключаться на чужой dev-сервер, чтобы скрыть неудачу сборки.

Создать frontend-tests.yml: Node 22, npm ci, playwright install --with-deps chromium webkit на Linux CI, npm run verify:frontend. Сохранять отчёт/trace как CI artifact при сбое, без реальных контактов. Общий quality workflow не менять.

Обязательные итоговые материалы:
- Скрины offer/preference/contact/received на 390px, Auto на 360/430 и desktop1280.
- Скрин хотя бы одного error-state и Beauty.
- Короткое видео Auto прохождения трёх шагов на синтетике.
- Ясная маркировка: browser-тесты с HTTP mock либо реальная интеграция. Не называть mock-получение настоящим lead в PostgreSQL.
- Файлы в docs/reports/screenshots и разрешённой папке видео; никаких node_modules, .env, dumps, trace с секретами в Git.

Если браузер/кодек недоступен, не придумывать свидетельства: закончить код и доступные проверки, указать конкретно отсутствующий артефакт и причину. Это остаточное ограничение, не автоматический зачёт теста.
