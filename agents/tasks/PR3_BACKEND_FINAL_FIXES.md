## 2. BR1 — последняя попытка очереди остаётся processing навсегда (P1)

Код: src/server/notifications/worker.ts:62, claimBatch.

Воспроизведено на отдельной настоящей PostgreSQL-БД:
- У outbox status=processing, attempts=8, lease_until в прошлом.
- runOutboxBatch возвращает processed=0, sent=0, retried=0, dead=0.
- Строка остаётся processing/8/expired=true.
- Причина: WHERE attempts < 8 исключает восстановление последней попытки.

Исправить:
- Любая истёкшая processing-задача должна получить определённый исход.
- Учесть два случая: crash до записи receipt и crash после COMMIT receipt, но до markSent.
- При уже существующей recording receipt согласованно завершить задачу, сохранив единственное свидетельство.
- При исчерпанных попытках без свидетельства допустим явный dead с безопасной причиной и документированным операторским действием. Бесконечного processing и скрытой девятой отправки быть не должно.
- Stale claim token по-прежнему не изменяет более новую попытку.
- Проверить бюджет пачки: сейчас 20 задач выполняются последовательно при lease=120 с и timeout=10 с. Не начинать отправку с уже потерянным claim; выбрать ограниченную конкурентность, продление lease либо другой согласованный способ внутри имеющегося контракта. Внешнюю отправку не выполнять под SQL-транзакцией.

Обязательные регрессии:
| ID | Сценарий | Проверяемый результат |
| --- | --- | --- |
| BR1a | Crash на попытке 8 до receipt; lease истёк | Детерминированный terminal/recovery outcome, processing не остаётся |
| BR1b | Receipt записана на попытке 8, crash до sent | Одна receipt, согласованное завершение outbox |
| BR1c | Два worker восстанавливают последний expired claim | Один действующий владелец, нет потери/перезаписи |
| BR1d | Медленная пачка и истечение lease | Не отправляется задача с утраченным claim; lease-бюджет проверен |
| BR1e | Обычный отказ попытки 8 | Dead, без автоматической попытки 9 |

Проверять настоящий PgOutboxRepo, SQL-строки и claim token, а не только decideAfterFailure.

## 3. BR2 — guard проверяет не тот DSN и допускает переопределение host (P1)

Код: scripts/backend/migrate.ts:22–23; src/server/config/guards.ts:12.

Два подтверждённых случая:
1. При LSF_MIGRATE_TEST_MODE=1, безопасном TEST_DATABASE_URL и другом DATABASE_URL мигратор проверяет первый, а подключается ко второму. На собственной пустой локальной БД с именем без lsf_test_ реально создано 5 таблиц; процесс завершился 0.
2. assertSafeTestDatabaseUrl принимает URL с hostname=127.0.0.1 и query host=example.invalid, тогда как установленный PostgreSQL-парсер выбирает effective host=example.invalid. Для этой проверки использован только parser, внешнего подключения не было.

Исправить:
- Валидировать именно фактическую строку/конфигурацию, с которой будет открыто соединение.
- В test mode несовпадение DATABASE_URL и TEST_DATABASE_URL не должно обходить проверку.
- Ограничить протокол PostgreSQL и effective target: host и database после разбора драйвером.
- Параметры URI не должны перенаправлять соединение за разрешённый loopback или в другую БД.
- Все harness/вспомогательные тестовые подключения, очистки и restore используют тот же проверенный effective DSN.
- Не проверять небезопасную строку пробным подключением. Отказ происходит до Client.connect и любых SQL.

Регрессии:
| ID | Сценарий | Результат |
| --- | --- | --- |
| BR2a | Safe TEST_DATABASE_URL, unsafe DATABASE_URL, test mode | Nonzero; connect/SQL не выполнялись |
| BR2b | host в query отличается от URL hostname | Отказ до соединения |
| BR2c | Не PostgreSQL-протокол, не loopback, имя без lsf_test_ | Отказ |
| BR2d | Корректный loopback DSN с допустимыми опциями | Миграции работают |
| BR2e | Обычный production migration mode | Сохраняется явно разрешённая эксплуатационная команда; test-guard не подменяет production-политику |

CLI-регрессия BR2a обязана вызывать реальный migrate.ts. Не ограничиваться вызовом guard-функции.

## 4. BR3 — экспорт можно записать внутри Git через .. (P2)

Исправить:
- Сначала получить фактический нормализованный абсолютный путь, затем проверить границу.
- Учесть dot segments, регистр/разделители по правилам ОС и существующий родительский путь.
- Ссылка/junction снаружи, ведущая внутрь checkout, не должна обходить проверку.
- Допустимый путь действительно снаружи должен работать, включая ../outside.csv после корректного разрешения.
- Сохранить wx/no-overwrite, безопасные права файла и отсутствие контактов в stdout.

Регрессии: прямой путь внутри; outside/../inside; вложенный вариант; допустимый абсолютный/относительный снаружи; повторный файл; symlink/junction при поддержке ОС с явным объяснением ограничения. В запрещённых случаях проверять отсутствие созданного файла реальным CLI.
