## 2. FR1 — таймаут должен действовать до получения всего ответа (P1)

Код: src/features/booking/client/lead-client.ts:100–107 и чтение error body.

Причина: clearTimeout выполняется сразу после await fetch, до await response.json. fetch завершается на заголовках; если тело приходит частично и зависает, 15-секундная защита уже выключена.

Фактическая диагностика с настоящим локальным HTTP-сервером:
- Сервер немедленно отдаёт заголовки 201 application/json и начало JSON, затем не закрывает body.
- submitLead запущен с timeoutMs=500.
- Через 1000 мс headersReceived=true, outcome=pending; ожидался timeout.
- Соединение завершено только очисткой фикстуры.

Исправить:
- Один дедлайн покрывает connect/headers/body/JSON, включая HTTP error body.
- Abort инициирует прекращение чтения и конечный SubmitError kind=timeout.
- Внешний AbortSignal корректно отменяет ожидание; listener/timer очищаются во всех ветках.
- Нельзя оставлять submitting навсегда, запускать скрытый повтор или терять snapshot/idempotencyKey.
- Сохранить default 15000 и управляемый timeoutMs для тестов.

Регрессии с настоящим submitLead:
| ID | Сценарий | Результат |
| --- | --- | --- |
| FR1a | Не приходят заголовки | Timeout |
| FR1b | Пришли 201 headers, body завис | Timeout, управляемое завершение |
| FR1c | Пришли 503 headers, error body завис | Timeout, форма сохраняется |
| FR1d | Тело дошло до дедлайна | Успех/HTTP error без позднего abort |
| FR1e | Внешний signal до/во время fetch/body | Корректная отмена и cleanup |
| FR1f | Повтор после неизвестного исхода | Прежний key и payload, один итоговый результат |

Подменить fetch/HTTP можно в тесте, но не заменять сам submitLead или его поведение. Положительный тест на обычный AbortController не засчитывается.

## 3. FR2 — невалидная квитанция ошибочно показывает успех (P1)

Код: lead-client.ts:49–59.

Настоящий browser-тест через HTTP fixture вернул:
~~~json
{"leadId":"not-a-uuid","status":"received","replayed":false,"message":"Заявка получена."}
~~~
UI показал lead-success, хотя LeadReceipt schema требует format=uuid. Это подтверждённый случай ложного успеха на некорректном ответе.

Исправить guard по текущему контракту:
- leadId — UUID допустимого wire-формата.
- status строго received, replayed boolean.
- message — строка 1..300.
- Поля обязательны, неверные типы/null/массивы/неизвестные поля отклоняются согласно additionalProperties=false.
- 200/201 без валидной квитанции → invalid-response, без экрана успеха, форма и возможность безопасного retry сохраняются.
- Не выводить сырое HTML/body прокси пользователю.

Регрессии: корректные 200/201/replayed; не-UUID; пустой/слишком длинный message; null/array; неверные status/replayed/типы; дополнительные поля; HTML/битый JSON. Проверять и реальный guard/transport, и отсутствие lead-success в браузере.

## 4. FR3 — серверные ошибки предыдущего шага скрыты; focus не управляется (P1/P2)

Код: state.ts SUBMIT_ERROR, BookingFlow.tsx и ContactStep.tsx.

Подтверждённые browser-наблюдения:
1. На contact сервер отвечает 422 VALIDATION_FAILED с fieldErrors.preferred.time. На странице виден только общий текст «Проверьте поля формы», конкретная ошибка не видна, остаётся contact, focus=BODY.
2. При пустом телефоне focus после submit также BODY; у input нет aria-describedby на текст ошибки.

Исправить:
- Маршрутизировать fieldErrors serviceId/resourceId/serviceOptions/preferred на шаг параметров либо показать доступную конкретную сводку с переходом к полю.
- customer.phone/customer.name/consent ошибки показывать на contact.
- Возврат из API-ошибки сохраняет контакт/совместимые данные, не отмечает согласие автоматически и не делает новый POST.
- После локальной/серверной ошибки focus — на первом ошибочном поле либо доступном error summary, затем доступен переход к полю.
- Тексты ошибок связать стабильными id и aria-describedby. aria-invalid отражает актуальное состояние.
- Поле preferred без суффикса и вложенные serviceOptions обрабатываются явно.
- После исправления ошибки и повторной отправки сводка/payload/ключ соответствуют текущим данным.
- Не выполнять безусловный GO_TO_STEP, который стирает только что полученные fieldErrors.

Регрессии:
| ID | Сценарий | Проверка |
| --- | --- | --- |
| FR3a | Локально пустой/неверный телефон | Нет POST, видимый текст, focus/association |
| FR3b | 422 customer.phone/name/consent | Соответствующие поля contact |
| FR3c | 422 preferred.time/date/preferred | Конкретная ошибка видна, доступно исправление, контакт сохранён |
| FR3d | 422 serviceId/options/resourceId | Переход/summary ведёт к правильному полю |
| FR3e | Ошибок несколько | Читаемая сводка и предсказуемый focus |
| FR3f | Исправление и retry | Новый payload/ключ по контракту, один POST |

409 CONFIG_CHANGED/CONSENT_CHANGED проверить отдельными сценариями: никаких автоматических повтора/согласия/перезагрузки; пользователь понимает, как обновить сведения и что произойдёт с вводом. Обычный повтор старого запроса не должен быть единственным предлагаемым действием.

## 5. FR4 — унаследованные ключи конфигурации дают 500 вместо 404 (P2)

Код: src/config/sites/index.ts:11 и metadata/page/privacy.

Подтверждено настоящими HTTP GET объединённого Next production app:
| Путь | Сейчас | Нужно |
| --- | --- | --- |
| /demo/constructor | 500 | 404 |
| /demo/toString | 500 | 404 |
| /demo/__proto__ | 500 | 404 |

Причина: configs[siteKey] читает свойства Object.prototype, а nullish fallback не отсекает возвращённую функцию/объект.

Исправить:
- Явный lookup только собственных разрешённых ключей, например Map либо Object.hasOwn.
- Одинаковое поведение page, metadata и privacy.
- Пустой/повреждённый конфиг не передаётся в BookingFlow и не падает на config.hero/services.
- Не добавлять публичные test/mock-маршруты для проверки ошибочных конфигов.

Тесты: auto/beauty доступны; обычный unknown и три ключа выше → 404; privacy для них → 404; unit fixtures повреждённого/пустого конфига; noindex соответствует режиму.

## 6. FR5 — заменить тесты, проверяющие константы вместо приложения (P1 для приёмки)

Зелёные 20/20 и 56/56 подтверждены, но часть имён сценариев не соответствует фактическим assert.

Конкретно:
- FU15 проверяет локальное выражение state.submitState === submitting, не число реальных transport calls.
- FU16 сравнивает две написанные в тесте строки, не обработку позднего ответа.
- FU18 конструирует SubmitError, не проверяет response → error mapping submitLead.
- FU19 передаёт retryAfterSeconds в конструктор, не разбирает заголовок Retry-After.
- FU20 создаёт объект timeoutError, не запускает timeout/abort.
- FE19 проходит только переход offer → preference, хотя заявлена клавиатура всех шагов/radio.
- FE21 меняет viewport, но не выполняет заявленный zoom 200%.
- FE22 не создаёт длинную услугу/ошибку и отсутствие картинки, проверяет обычные radio.
- FE26 проверяет storage/URL, но не подписывается на console и не проверяет его.
- FE27 не проверяет новый idempotency key, хотя это указано в отчёте.

Требования:
1. Вызывать настоящую проверяемую логику/компонент/transport. При необходимости выделить небольшой чистый helper из BookingFlow, сохранив публичный контракт.
2. Для late response управлять двумя реальными Promise и проверить, что старая попытка не меняет новое состояние.
3. Для двойного submit считать фактические запросы, в том числе Enter/повторный click.
4. Для HTTP mapping передавать контролируемые Response для всех кодов и malformed response.
5. Retry-After: отсутствие, ноль/отрицательное, мусор/частичное число, корректное целое; без доверия parseInt к произвольному суффиксу.
6. Сценарии layout содержат фактические длинные fixture-данные и ошибку; для zoom выполнить сам zoom и проверить достижимость полей/CTA.
7. В console/storage/URL-проверке использовать синтетические маркеры и подписку до заполнения формы.
8. Новый lead после успеха действительно имеет другой UUID и очищенные контакт/согласие.
9. Обновить матрицу ID → фактический тест/подслучай; не заявлять покрытие, если assert проверяет только соседнее свойство.

Не добавлять passWithNoTests, skip, ослабленные ожидания, глобальные задержки для сокрытия гонок или новые зависимости.
