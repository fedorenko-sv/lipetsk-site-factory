# ТЗ разработчику 1 — интерфейс PR-3 Auto

Историческое сводное ТЗ. Для текущего полного блока действует [PR3_FRONTEND_ANTIGRAVITY.md](PR3_FRONTEND_ANTIGRAVITY.md); остановки после отдельных F1/F2/F3 больше не применяются.

## Запрос для запуска

Ты — разработчик интерфейса Lipetsk Site Factory. Работай в ветке codex/frontend-pr3 и отдельном checkout. Прочитай AGENTS.md, архитектуру, HTTP-контракт и это ТЗ. Реализуй три мобильных шага PR-3 Auto до готовности к интеграции; backend ведёт второй разработчик, контрактом и main владеет архитектор. Дополнительных агентов не запускай.

Не переустанавливай каркас и не заменяй стек. Не коммить в main. При несовместимости контракта опиши её архитектору и продолжай независимую часть.

## Результат

/demo/auto показывает три шага: оффер/прайс → услуга/предпочтение → телефон/согласие/результат. Данные берутся из конфига. Ошибка не стирает форму; успех показывает leadId только из API. Beauty использует тот же BookingFlow и HTTP-клиент хотя бы в минимальном проверочном варианте.

Канал получения заявок выбирает заказчик в серверной настройке. Интерфейс и HTTP-клиент не зависят от Telegram/почты/CRM и не передают канал или получателя в body. Текст успеха остаётся общим: заявка получена, время подтвердит администратор.

## Твоя область

Создать/изменять:

- src/app/page.tsx — навигация демо или redirect на разрешённое Auto.
- src/app/layout.tsx, src/app/globals.css — общая оболочка и CSS.
- src/app/demo/[siteKey]/page.tsx, privacy/page.tsx — конфиг, режим, metadata, демо-политика.
- src/features/booking/ui/BookingFlow.tsx, OfferStep.tsx, PreferenceStep.tsx, ContactStep.tsx.
- src/features/booking/ui/{PhoneField,ServiceSummary,RequestResult}.tsx — небольшие компоненты по необходимости.
- src/features/booking/client/lead-client.ts — только транспорт и обработка HTTP.
- src/config/sites/{auto,beauty}.ts — импорт данных из проверенных примеров, без серверных назначений.
- src/themes/{technical,editorial}.css, src/components/**, public/demo-assets/**.
- tests/ui/**, tests/e2e/**, docs/reports/frontend.md — результаты своей работы.

Не трогать src/app/api/**, src/server/**, db/**, contracts/** и общие зависимости. Согласованные типы генерирует архитектор из OpenAPI; не заводить ручную вторую модель запроса.

## Порядок задач

### F1. Изучить старт и конверсионные ориентиры

- [ ] Проверить текущую ветку, чистоту чужих файлов и запуск npm ci.
- [ ] Прочитать docs/01-product-scope.md, docs/02-architecture.md, docs/03-api-contract.md.
- [ ] В браузере проверить доступные CARSTAR, Topaz и Fresha на мобильной ширине без отправки форм; записать 3–5 коротких наблюдений в свой отчёт. Если ресурс не открывается, отметить ограничение и продолжить.
- [ ] Выбрать оригинальную technical-тему: графит, читаемый светлый текст, один функциональный акцент; не копировать бренды/фото/композицию сайта целиком.
- [ ] Собрать OfferStep и статические состояния шагов 2–3. Сделать три кадра 390px с маркировкой прототипа.

Приёмка: видны оффер, 3–5 цен и CTA; контент синтетический и помечен; нет чужих логотипов и выдуманного доверия.

### F2. Управляемый BookingFlow

- [ ] Одна структура состояния: step=offer|preference|contact; serviceId; serviceOptions; resourceId?; preferred?; customer; consentAccepted; submitState.
- [ ] Смена услуги сбрасывает несовместимые параметры/ресурс. Возврат назад сохраняет совместимый ввод.
- [ ] Услуга, параметры и цена читаются из SiteConfig. Сервер позже перепроверяет их.
- [ ] Для Auto ресурс скрыт. Для Beauty доступен optional-выбор мастера из конфига.
- [ ] Дата и время — подходящие пожелания в Europe/Moscow. Показывать текст ручного подтверждения рядом с выбором и в сводке.
- [ ] Пустые услуги, неактивный конфиг и длинные названия дают понятный интерфейс, не сломанный select.

Приёмка: ровно три обязательных шага; результат внутри шага 3. Условие «дата/время обязательно» идёт из booking.preferenceRequired, а не из JSX под Auto.

### F3. Форма и API-клиент

- [ ] Телефон type=tel/inputMode=tel, читаемый label, форматирование без ловушек вставки; окончательная проверка на сервере.
- [ ] Имя необязательно. Согласие по умолчанию false, версия из конфига, ссылка на соответствующую политику.
- [ ] Сводка видна до отправки; без обещания фиксированного времени/неподтверждённого SLA.
- [ ] Перед отправкой создать UUID. Хранить ключ и данные при timeout/неизвестном исходе.
- [ ] Отправить POST /api/leads с JSON и Idempotency-Key. Таймаут 15 секунд через AbortController. Автоматически не запускать бесконечные повторы.
- [ ] Повтор неизменённого запроса после сетевой ошибки использует прежний ключ; изменение данных или исправление 422 — новый.
- [ ] На 200/201 показать requestId/leadId из ответа по назначению: leadId для результата, requestId только для ошибки/поддержки.
- [ ] На 422 показать fieldErrors; на 409 предложить обновить сводку/согласие; 429 учитывает Retry-After; 503/timeout сохраняет ввод.
- [ ] Кнопка блокируется на время отправки. Нельзя показывать успех по setTimeout или при отсутствии backend.
- [ ] При demo-режиме явно предупредить, что вводится только +70000000000. До demo-backend отправка недоступна/показывает честный DEMO_NOT_READY.
- [ ] Контакты не сохранять в localStorage/URL/аналитику. Состояние в памяти, перезагрузка может очистить контакт.

Контракт клиента по смыслу:

```ts
// Типы Request/Response генерируются из contracts/openapi.json.
type SubmitTransport = (
  body: LeadCreateRequest,
  idempotencyKey: string,
  signal?: AbortSignal
) => Promise<{ status: 200 | 201; body: LeadReceipt }>;
```

Ошибка транспорта должна сохранить HTTP code/error envelope, чтобы UI не разбирал текст сообщения. Итоговую сигнатуру согласовать в узком клиентском файле, не менять серверный контракт.

### F4. Доступность, повторное использование, качество

- [ ] Тесты UI проверяют переходы, ошибки, повтор/ключ и сохранение ввода; не просто совпадение снимка JSX.
- [ ] Browser-тест: offer → preference → contact → received с тестовым HTTP transport; второй тест — 503, сохранение данных и повтор.
- [ ] Размеры 360/390/430/1280, focus на заголовок нового шага, aria-live для результата, label и ошибки у полей, кнопки ~44px, видимый focus и контраст.
- [ ] Проверить клавиатуру, zoom 200%, отсутствие изображений, длинные данные, slow network и WebKit.
- [ ] Минимальный Beauty-конфиг проходит тот же путь без копирования BookingFlow, lead-client и валидации.
- [ ] Внешняя аналитика выключена. Допустим локальный typed/no-op адаптер с allowlist событий без произвольных строк и PII.
- [ ] Сдать итоговые кадры трёх шагов и desktop; после интеграции обновить их по фактической версии.

## Проверки и команды

Каркас: npm run verify:architecture. После общего коммита тестовых инструментов:

```powershell
npm run test:ui
npm run test:e2e
npm run lint
npm run typecheck
npm run build
```

Добавление этих scripts и зависимостей делает архитектор одним общим коммитом; до него не писать отчёт, что команды уже существуют.

Минимальный тест поведения после выбора используемой библиотеки:

```ts
test("повтор после timeout сохраняет данные и ключ", async () => {
  // Установить транспорт: первая попытка timeout, вторая 200 с прежним leadId.
  // Пройти три шага, заполнить синтетический телефон и согласие.
  // Нажать «Отправить», дождаться ошибки, затем «Повторить».
  // Проверить одинаковый Idempotency-Key, прежний payload и один результат.
});
```

Это сценарий для реализации теста, не готовый/уже пройденный тест. Проверки реальной БД и доставки выполняет серверный агент и затем архитектор в общем прогоне.

## Формат сдачи

Ветка + SHA/PR; список пользовательских изменений; фактические команды и результаты; viewport/браузеры; пути к скринам; известные ограничения; подтверждение отсутствия реальных контактов/секретов. При нехватке backend статусы честные, mock только в тестах.

Готовность разработчика означает ready-for-integration; финальное release-ready назначает архитектор.
