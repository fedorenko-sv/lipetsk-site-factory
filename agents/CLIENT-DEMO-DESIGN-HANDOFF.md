# Lipetsk Site Factory. Передача дизайнеру и архитектору клиентских демо

Снимок проекта на 22 ноября 2026 года. Базовый коммит кода `87370e3c534c5e9c296840844d094efe8ce73b1b`. Рабочая ветка `codex/six-prototypes`, [репозиторий](https://github.com/fedorenko-sv/lipetsk-site-factory), [PR #5](https://github.com/fedorenko-sv/lipetsk-site-factory/pull/5).

## Задача агента

Ты дизайнер продукта и фронтенд-архитектор. Предложи и проверь способ быстро готовить персональные демонстрационные сайты для локального бизнеса на уже работающей фабрике. Из одного набора компонентов и сценариев нужно получать сайты, которые выглядят как продукты конкретных компаний. Для типового клиента оператор выбирает подходящую оболочку, подставляет название, логотип, цвета, шрифты и материалы и получает отдельный показ. Ориентир исходного продукта — 30–60 минут при готовых материалах. Это гипотеза для замера, а не достигнутый показатель.

Начни с аудита кода и нескольких реальных страниц. Затем сравни варианты архитектуры, подготовь карту того, что менять, и проверь выбор небольшой реализацией в своей ветке. После доказательства идеи составь порядок подключения остальных направлений. Итог должен позволять другому разработчику повторить замену бренда по инструкции.

## Что за продукт

Владелец знакомится с локальными компаниями и показывает мобильное демо под конкретную задачу. Оно помогает обсудить оффер, первую страницу и форму заявки, а затем перейти к клиентскому внедрению. Проект экономит время за счёт общей кодовой базы, готовых отраслевых оболочек и повторно используемых бизнес-сценариев. У каждой оболочки своё оформление, содержание и навигация. Каждый клиентский запуск отдельно определяет подтверждённые данные, среду и канал заявок.

| Пример | Вход от витрины | Страниц | Основной сценарий |

| A2 MIRA Beauty | `/demo/beauty` | 9 | Стрижка или маникюр, мастер по желанию, предпочтительное время. |

В каждой основной оболочке есть главная, каталог с карточками, профильные информационные страницы, отдельная форма и политика. В последнем пакете добавлены 42 иллюстрации WebP, вымышленные профили, примеры выбора и расширенные галереи. Все демонстрационные материалы следует обозначать как синтетические. ### Общие ядра

- **Core A Booking.** Оффер и цена → выбранная услуга, параметры, специалист и пожелание по времени → контакты, согласие, квитанция. Ссылка из карточки переносит service/resource в форму после проверки совместимости. Дата и время означают пожелание. У Stay речь о времени разговора, у Sports ёмкость группы не проверяется. Сервер принимает `POST /api/leads` с версией конфигурации и ключом идемпотентности.
- **Core B Calculator.** Параметры окна → детализация предварительной цены → контакт, согласие, квитанция. `POST /api/estimates` передаёт параметры. Сервер повторно считает сумму целыми копейками и сохраняет снимок параметров, расчёта и версии формулы.
- **Сервер заявок.** Проверяет Origin, схему, scope и версии, применяет ограничения частоты. PostgreSQL атомарно сохраняет заявку и outbox, повтор возвращает существующую квитанцию, worker обрабатывает уведомление с повторными попытками. Сейчас получатель — локальный recording-адаптер, который подтверждает обработку тестовыми данными. Для клиента канал выбирается отдельно между подходящим адаптером CRM, email или мессенджера.
- **Core C Catalog/RFQ.** Будущий сценарий B2B-каталога и запроса коммерческого предложения. Архитектура айдентики может оставить место для новой оболочки, работа над Core C в этот пакет не входит.

Демо принимает только синтетический номер `+70000000000`. Квитанция означает запись заявки в БД. Для реальных визитов, ночей, оплаты и сообщений нужны отдельные пользовательские сценарии и подтверждённые условия. Запуск с клиентскими данными, публичный HTTPS и постоянная удалённая БД — следующий этап после готовности демо. ## Как открыть проект

В новом клоне или отдельной рабочей папке. Нужны Node.js 22, npm и Docker с Linux engine для PostgreSQL.

~~~powershell
git clone --branch codex/six-prototypes --single-branch https://github.com/fedorenko-sv/lipetsk-site-factory.git
cd lipetsk-site-factory
npm ci
npm run db:test:up
npm run build
npm run preview:portfolio
~~~

Витрина будет на [127.0.0.1:3035](http://127.0.0.1:3035/). После сборки можно запустить отдельный профиль в своём терминале.

~~~powershell
npm run preview:demo -- --list
npm run preview:demo -- beauty
~~~

Beauty открывается на [127.0.0.1:3042](http://127.0.0.1:3042/). Другие порты от 3041 до 3046. При занятом порте можно добавить `--port 3142`. Отдельный процесс получает собственные origin и тестовую БД, сервер валидирует точный allowlist. Исключение в составе профиля Auto — связанный OBLIK. В фабричном режиме доступны все демо. `DEMO_SITE_KEY` сейчас выбирает существующую оболочку и её scope. Файлы под `/demo-assets/` общедоступны на сервере. [Механика запуска и изоляции](../docs/17-isolated-demo-profiles.md)

### Текущее состояние айдентики

1. Внешний вид обычных оболочек задан через `--p-*` и классы `.prototype-*` в `src/features/prototypes/styles.css`. Формы используют `--bg-*`, `--text-*`, `--border-*`, `--color-accent` и состояния из `src/themes/`. В `styles.css` есть мост переопределения внутри `.prototype-booking-host`. Проверь специфичность, интерактивные состояния и вложенные темы.
2. OBLIK использует `--dt-*`, несколько CSS-файлов и отдельные переопределения формы. В Calculator часть палитры, полей и схемы задана напрямую. Диалоги галереи и мобильное меню тоже нужно проверить при смене светлой/тёмной темы.
3. Оболочки и витрина используют локальные гарнитуры под CSS-именами `Oblik Sans` и `Oblik Serif`. В `public/demo-assets/detailing/fonts/` лежат файлы WOFF2, резервные TTF, манифест и лицензии. Имена гарнитур и размеры встречаются напрямую в стилях. Фонт нужно менять вместе с отступами текста, высотой строки, весами и метриками fallback.
4. Название может идти из `catalog.ts`, SiteConfig, компонентов или metadata маршрута. Логотип, шапка, подвал, заголовки, изображения, подписи и открытия отдельных страниц подключены разными путями. Нужно провести инвентаризацию реальных источников имени и логотипа, включая политики, состояние формы, браузерный title и карточку общей витрины.
5. У оболочек разная композиция: редакционная Beauty, яркая Sports, спокойная Medical, полноэкранный Stay, технические Auto и Estimate, кинематографичный OBLIK. Смена бренда должна сохранять пригодную для отрасли структуру и сценарий. Копирование страниц по каждому client key быстро разойдётся по поведению.

## Каким должен стать механизм

Сравни как минимум два подхода. Для первого этапа кандидат по умолчанию — **валидируемый конфиг бренда в Git, локальные ассеты и CSS custom properties на корневом контейнере оболочки**. Рассмотри отдельно управление набором заранее собранных конфигов во время запуска. Укажи, что потребует новую сборку, что сможет меняться запуском, как это влияет на SSR, кэш, аудит и откат. Напиши короткий ADR с выбором и ценой альтернативы. Если выбираешь другой вариант, покажи, что он проще для оператора и не дробит уже работающие маршруты.

Предлагаемое разделение. Это рабочая гипотеза для проверки в прототипе.

~~~mermaid
flowchart TD
    S["Отраслевая оболочка · страницы, компоновка, ядро"] --> R["Сервер определяет разрешённый дизайн"]
    B["Клиентская айдентика · название, логотип, палитра, шрифты"] --> R
    M["Редакторские материалы · изображения, подписи, тексты"] --> R
    R --> UI["SSR · scoped CSS variables, компоненты и метаданные"]
    C["Конфигурация услуг или ставок"] --> UI
    C --> API["Сервер заявки проверяет услугу и цену"]
    UI --> API
    E["Приватное окружение · scope, БД и доставка"] --> API
~~~

- **Оболочка** определяет композицию, разделы, тип действия и поведение. **Бренд** определяет то, что посетитель видит в атрибутах компании и визуальных ролях. Услуги, ставки, согласие и версия рабочего контракта используют соответствующий конфиг. Если нужен текстовый блок клиента, размещай его в редакторских данных. Секреты и назначения уведомлений остаются в приватной среде.
- **Схема бренда.** Предложи пример `BrandConfig` с версией схемы, уникальным ключом и явной совместимостью с оболочкой. Нужны краткое/полное название, вариант логотипа для светлого и тёмного фона или текстовый fallback, выбранные семейства и веса шрифтов, палитра, поля метаданных и явные ссылки на подтверждённые публичные ассеты. Укажи обязательные поля, опциональные и порядок разрешения fallback. Публичное имя не подменяет оператора данных и согласованные юридические сведения.
- **Токены в три слоя.** Сырые значения → роли интерфейса → точечные настройки компонента. Опиши карту для фона, поверхности, текста и приглушённого текста, границы, акцента и текста на нём, фокуса, ошибки, успеха и отключённого состояния. Для типографики — display/body, веса, fallback, межстрочный интервал и проверка кириллицы/цифр. Радиусы и интервалы можно выводить из пресета оболочки. Задай типовые пары контраста, которые валидирует конфиг.
- **Миграция без копирования.** Покажи соответствие новых ролей текущим `--p-*`, `--dt-*` и токенам формы. Сначала связывай роли через мост рядом с контейнером, постепенно заменяй прямые цвета в компонентах. Бренд должен проходить в шапку, форму, галерею, подвал и метаданные из одного источника. Отраслевым вариантам нужны осмысленные различия в компоновке.
- **Правила применения.** Бренд резолвится до первого отображения, чтобы исключить вспышку темы и рассогласование SSR. Обсуди ключи кэша и детерминированные fallback для отсутствующей и неверной конфигурации. Цвета — ограниченные форматы или проверенные палитры, гарнитуры — разрешённый каталог файлов, изображения — подтверждённые пути внутри набора ассетов. В конфиге должны быть данные, пригодные для валидации. Свободные CSS/HTML, исполняемые строки и произвольные внешние ассеты сюда не относятся.
- **Изоляция показов.** Поиск бренда ограничен выбранным профилем. Выбирать бренд можно из зарегистрированных конфигов, без расширения API allowlist или изменения `siteKey`, `serviceId` и правил цены. Сравнение двух брендов следует делать на разных превью или на явно предусмотренной тестовой странице. Смену бренда и подбор публичной среды рассматривай отдельно от многопользовательского кабинета.
- **Откат и эксплуатация.** Добавить клиента можно копированием только примера конфига, файлами логотипа/шрифтов/фото и выбором оболочки. Откат возвращает прежний ключ или предыдущую версию конфига. Укажи доступный оператору способ запуска, диагностику плохих входных данных, процедуру обновления материалов и измеримое время подготовки.
- **Дизайн.** Выбери типографику, палитру и фотостиль, различимые визуально на трёх контрольных экранах от каталога до квитанции. Покажи, как выдерживаются длинное название, логотипы разных пропорций, контраст ошибочного поля, доступный focus и дата/цена на мобильном. Сохрани управление видео и reduced motion там, где они уже есть. Советы из аудита от 19 ноября используй как входные наблюдения. Расширение каталога и реальная запись остаются отдельными задачами.

## Минимальный прототип и приёмка

1. **Сними исходное состояние.** Задокументируй, чем отличаются визуальные слои Auto или Beauty, Estimate и OBLIK. Снимки главной, каталога/карточки, формы и состояний ошибки. Разметь прямые литералы, существующие токены и места дублирования названия. Сверь доступность при клавиатурном проходе.
2. **Покажи два бренда одной оболочки.** Предпочтительно MIRA и новый вымышленный бренд той же Beauty. Различия должны быть видны в названии, логотипе, фоне, акценте, шрифтах, карточке, форме и заголовке вкладки. Используй общие маршруты, компоненты и один сценарий заявки. Сравни, сколько файлов меняет добавление второго бренда. Подключение другого цвета следует продемонстрировать и на ограниченном срезе Calculator, чтобы проверить применимость второй системе форм. OBLIK внеси в карту миграции с перечислением исключений по сценам.
3. **Покажи повторяемость.** Дай пример брифа клиента, один валидный пример конфига с лицензиями и ассетами, точные команды применения, проверки и отката. Проведи пробную адаптацию по своему runbook и запиши время, какие файлы менял и что пришлось делать вручную.
4. **Проверь поведение.** Ширины 360, 390, 768 и 1440 px, клавиатура и видимый фокус, 200% zoom, длинное имя, fallback без логотипа, недоступный шрифт, reduced motion, отсутствие горизонтальной прокрутки, собственные ссылки внутри профиля, корректные ошибки. Для нового кода проверь валидный, неизвестный и несовместимый бренд, отсутствие утечки токенов и имени при переходе между оболочками. Картинки имеют размер и понятный alt по смыслу. Убедись, что загружаются только нужные гарнитуры.
5. **Пройди заявку и калькулятор.** На двух вариантах проверь прежние payload/idempotency, выбранную услугу и специалиста, точный расчёт и сохранение контакта при восстанавливаемой ошибке. Достаточно синтетики и существующего проверочного recording. Если меняешь общий слой или runtime, проверь витрину, 69 маршрутов, шесть изолированных профилей и регрессию OBLIK. Никаких тестов, которые просто сравнивают CSS с самим собой.
6. **Сдай результаты.** Короткое решение в ADR, карта затронутых файлов, один PR с прототипом, примерами и инструкцией, пары сравнимых скриншотов на 390 и 1440 px, измерение времени, команды и фактические результаты тестов. Отдельно перечисли ограничения и вклад каждой следующей миграции. Предлагай небольшие последовательные изменения по оболочкам.
